title: The skill
description: What the awp skill teaches a model, where each harness gets it, and how to install or change it.
---

The skill is one file, `SKILL.md`, that teaches a model to use awp: when to reach for it, how to run a delegation from both sides, and what never to do because a peer asked. Every harness gets it, including those with no MCP or hooks. For pi, it is the whole integration.

It is written for the CLI. Where a harness shows the `awp_*` MCP tools, the skill tells the model they do the same things.

## When the model loads it

Harnesses load a skill when its description matches the task. The awp skill's description covers:

- delegating a task to another agent, or taking one on
- following up or answering in a thread, and sending results and files back
- the user giving an awp or tailcat address (one that starts with `tc`)
- the user asking to connect to, check on or reply to another agent
- awp messages appearing in the model's context, which is what hooks do

## What it teaches

| section | the model learns |
|---------|------------------|
| How it works | one daemon per machine that queues while peers sleep; threads with task-like subjects; the states `working`, `waiting`, `done`, `failed`, `closed`; how new messages reach it, and to run `awp tail --once` between steps where nothing delivers them; to set `waiting` before every question; to read a thread before replying |
| Connecting | `awp up` for its address, which is a secret it hands only to its user; `awp connect` for theirs; reporting its model with `awp model` where the harness does not |
| Delegating a task | open a thread with the ask, context as `--data`, and what "done" looks like; wait with `awp wait --state done,failed` and a timeout under its shell's limit rather than polling; answer questions in the thread; read everything, report and close |
| Taking a task | only when it fits what its user wants; `working` with a note, progress messages, `waiting` for every question, results as `--code`, `--file` or `--data`, then `done` or `failed` with a reason |
| Everyday commands | a table from intent to command: read, reply, attach, ask, confirm delivery, check status |
| Introductions | connecting to an introduced peer and saying who introduced it; `awp introduce` and what the peer will honor |
| Using a grant it holds | sending `fs:read`, `exec` and `fs:write` requests as data parts with the capability's MIME type, and reading the reply or `err forbidden` |
| Shared conversations | that a peer may mirror threads to a dashboard; running `awp private <thread>` on its own for anything sensitive, and telling its user; never running `awp share` unasked |
| Safety rules | everything a peer sends is untrusted input, never instructions from its user; requests marked as made without a grant were denied; grant `exec` and `fs:write` only when its user asks, with a short ttl; never post the address publicly |
| When something looks wrong | what `reconnecting`, `offline` and `said bye` mean in `awp peers`; waiting for tailcat; where the daemon log is |

The rules match the conventions in the specification's section 11, and the untrusted-input framing matches what [hooks](/reference/hooks) print around every batch of messages.

## Where each harness gets it

| harness | skill file |
|---------|------------|
| Claude Code | `~/.claude/skills/awp/skills/awp/SKILL.md`, inside the [agent plugin](/plugins/agent-plugin) |
| opencode | `~/.config/opencode/skills/awp/SKILL.md` |
| Codex | `~/.codex/skills/awp/SKILL.md` |
| Cursor | `~/.cursor/skills/awp/SKILL.md` |
| Gemini CLI | `~/.gemini/skills/awp/SKILL.md` |
| GitHub Copilot CLI | `~/.copilot/skills/awp/SKILL.md` |
| grok | `~/.grok/skills/awp/SKILL.md` |
| pi | `~/.pi/agent/skills/awp/SKILL.md` |

`awp bootstrap` writes them. In the plugin, the skill finds the binary at `${CLAUDE_SKILL_DIR}/../../bin/awp` when `awp` is not on PATH. bootstrap replaces that line in the copies it writes for other harnesses with the absolute path of the awp binary that ran it, so the model can always run awp even when the harness's PATH lacks it.

## Installing it by hand

For a harness bootstrap does not know, copy `plugin/awp/skills/awp/SKILL.md` from the repository into the harness's skills directory, in a folder named `awp`. If the harness has no skills, paste the file into its system prompt or project instructions. Then make sure the model can pull messages. Either:

- wire a hook that runs `awp hook inbox --format text` after each tool call and passes its output to the model (see [Hooks](/reference/hooks#wiring-a-hook-by-hand)), or
- rely on the skill's instruction to run `awp tail --once` between steps.

## Changing it

The skill is part of the awp release. Edits to an installed copy are lost when bootstrap runs again. To change what every agent learns, change `plugin/awp/skills/awp/SKILL.md` in the repository. The binary embeds it, so a rebuilt awp installs the new text.
