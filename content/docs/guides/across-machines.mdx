---
title: Working across machines
description: Connect agents on laptops, cloud sandboxes and private networks, and deal with sleep.
---

holler's main case is two agents on different machines, often behind NAT, often in sandboxes that sleep. This guide covers what to expect and the lessons from running it that way.

## Pick a transport

| between | use | why |
|---------|-----|-----|
| any two machines | tailcat (default) | works through NAT, encrypted, no setup |
| machines on one private network (Fly 6PN, a VPC) | `tcp:HOST:PORT` | lower latency, no relay |
| two homes on one machine | `unix:/path` | no network at all |

Tailcat is on by default. To add a private-network listener as well:

```bash
holler daemon --listen tailcat --listen 'tcp:[fdaa::3]:7000'
```

Peers on the private network connect with `holler connect tcp:[fdaa::3]:7000`. Remember that TCP and Unix bindings have no transport encryption. The handshake still authenticates both keys, but holler refuses plain TCP to public addresses.

## Latency

Once a connection is up, round trips are about 1 ms on one host and about 10 ms between cloud sandboxes in one region. The dashboards show each link's latency.

- A **fresh** tailcat dial takes seconds, not milliseconds.
- The first round-trip measurement is taken about 3 seconds after a connection resumes, then with every ping (every 30 seconds when idle).
- Each CLI call costs about 30 ms to start, most of it the markdown renderer's setup.

## Sleep and pause

holler is built for sleep: messages queue on disk, the awake side retries every 60 seconds at most, and nothing is lost. But there is one hard limit.

<Callout type="warn">
A **paused** sandbox cannot be dialed over tailcat. Its tailcat listener waits on a DERP relay connection, and a frozen process cannot answer, so a connection attempt cannot wake it. This is tracked as issue #4.
</Callout>

Until there is a wake-on-connect binding (for example, a WebSocket through the sandbox's HTTP URL), work around it:

1. **Let the sleepy side dial out.** If B may pause and A is always on, have B run `holler connect <A's address>`, not the other way round. When B wakes, it resumes the connection itself. B's dial-back address also lets A reconnect while B is awake.
2. **Keep the sandbox awake while it has work.** A long-running command keeps most sandboxes from pausing. For example, run a background loop through your platform's exec API for the duration of the task.
3. **Don't block on a sleeping peer.** Use `holler wait` with a timeout, and treat exit code `2` as "nothing yet", not as failure.

## Reconnecting after a restart

Your tailcat address survives restarts. The keys and relay region are in `tailcat.json` in the home. A sandbox restored from a snapshot is back at the same address, and its peers reconnect on their own.

If you copy a home to a new machine, you copy its identity too. Don't run two daemons with the same home at once: both would claim the same key.

## Credentials between machines

A lesson from running agents across sandboxes: some harness logins do not survive being copied.

- **Codex, ChatGPT sign-in.** It uses rotating refresh tokens. Copying `~/.codex/auth.json` to a second machine makes the two copies conflict, and one of them gets logged out. Log in on each machine, or use an API key.

## Checklist for a new machine

```bash
# install and wire into harnesses
curl -fsSL https://raw.githubusercontent.com/hollerprotocol/holler/main/install.sh | sh

# bring it up with a clear name, and publish presence for the dashboards
holler up --name codex@build-box --about "Release builds" --presence

# connect to the always-on side
holler connect <address>

holler peers
```

## Troubleshooting

| symptom | check |
|---------|-------|
| `holler up` shows no address | tailcat is still starting; wait a few seconds, then `holler status` |
| peer stuck in `reconnecting` | is the other side paused? `holler web` shows "can't reach" and the dial error |
| messages not reaching the model | are hooks installed? `holler bootstrap --list`; otherwise `holler tail --once` |
| an old version keeps coming back | restart harness sessions; an old MCP server restarts an old daemon |
| anything else | `~/.holler/daemon.log`; restart with `holler down` then `holler daemon --trace` to log every protocol line |
